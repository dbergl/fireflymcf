# Recipe ops — reference

Generated by `python3 -m fireflymcf.ops_doc` from `recipe_ops.py`. Do not hand-edit; `tests/test_ops_doc.py` pins it.

A project file (`*.ffproj.json`) is an ordered list of ops. `fireflymcf compile` applies them to the stock image named by `base_sha256`, reseals, runs the gates and writes `mcf-*.bin`. `docs/AGENT-GUIDE.md` is the procedure; this file is the op vocabulary.

```json
{
  "schema": 1,
  "base_sha256": "<sha256 of the stock mcf.bin>",
  "build_name": "Jayco B-Van V13 my build",
  "ops": [
    {
      "id": "pump-name",
      "type": "rename_label",
      "params": {
        "object": 4,
        "old": "Water Pump",
        "new": "Pump"
      },
      "enabled": true,
      "note": "why this change was made"
    }
  ],
  "preview": {}
}
```

`id` must be unique; later ops reference earlier ones as `{"ref": "<id>"}` where a parameter says so. `enabled: false` keeps an op in the file without applying it. `note` is free text and never affects the bytes. Object indices are build-specific: find them on the owner's own firmware with `pages`, `labels` and `render`, never from another build.

**Hardware status** says whether the op's mechanism has run on the reference coach (Jayco B-Van, firmware 13.6). "Verified" is the op's default: `no` means the compile manifest lists it under `unverified` and the build needs a coach check with stock on the stick; some ops narrow it by parameter. `fireflymcf ops` prints this reference from the installed package.

## Same-size edits

Bytes change in place. Nothing moves, so no pointer needs repair. Lowest risk.

### assert_layout

Check, at its place in the recipe, that chosen records (by walk key, object and record, or label) sit at given absolute boxes, or that nothing on a page moved since an earlier snapshot. Changes no bytes.

- **Hardware status:** Check-only: changes no bytes, so there is nothing to run on a coach.
- **Proof:** `pagewalk.py`
- **Implementation:** `recipe_ops.AssertLayout`

| parameter | type | required | default | meaning |
|---|---|---|---|---|
| `root` | integer\|object | yes |  | page root object index or {"ref": op_id} |
| `switch_values` | object |  |  | optional {switch child base: value} for the walk |
| `slot_values` | object |  |  | optional {slot: value} for the walk |
| `expect` | array |  |  | records and their absolute box: {select, x?, y?, w?, h?} |
| `snapshot` | boolean |  |  | true: record the walk for a later unchanged_since |
| `unchanged_since` | string |  |  | id of an earlier snapshot of the same root |
| `except` | array |  |  | selects left out of the unchanged_since comparison |

Error codes:

- `BAD_PARAMS` — no form or more than one, a malformed select or expect entry, `except` without `unchanged_since`, or `unchanged_since` naming no earlier snapshot, or one of another root or other switch/slot values.
- `NO_MATCH` — a select names no record of the walk.
- `AMBIGUOUS` — a label select without `nth` names more than one record, or an {object, record} select a record drawn under several keys (each is listed).
- `LAYOUT_MISMATCH` — an `expect` field differs from the placed box (`pagewalk.describe` lines: expected box -> actual box and the delta).
- `LAYOUT_MOVED` — `unchanged_since` found records moved, restyled, gone or appeared (`pagewalk.describe` lines).

### remove_control

Park a control off the 480 px canvas by rewriting its attach records' y. Bindings stay.

- **Hardware status:** UNVERIFIED. Never flashed.
- **Proof:** `CompileResult.unverified`
- **Implementation:** `recipe_ops.RemoveControl`

| parameter | type | required | default | meaning |
|---|---|---|---|---|
| `object` | integer | yes |  | object index to remove (the child, not the attaching parent) |
| `park_y` | integer |  | 900 | y coordinate written into every attach record; must be >= 480 |

Error codes:

- `BAD_PARAMS` — park_y < 480 (would not actually leave the visible canvas)
- `NO_SUCH_RECORD` — no object in the file holds an actual wtype-5 attach record with `child_index == object`. `insert.object_child_graph` is wtype-agnostic (it also surfaces wtype-6/0x2e container-child references), so it is used only as a cheap candidate pre-filter here; the real gate is a hit count over each candidate's own decoded records, matching `MoveElement`'s pattern of counting real hits rather than trusting candidate presence. An object reachable only via a wtype-6/0x2e reference (e.g. a type-6 switch's candidate list) is correctly refused, not silently no-opped.
- `NO_FIELD` — a parent's attach record for `object` was found but has no geometry `y` field to rewrite (unexpected shape; refuse rather than silently leaving that parent's attachment visible)

Error codes:

- `INSERT_REFUSED` — insert.insert_object refused the attach (bad parent, no wtype-5 container template on `parent`, etc.)
- `NO_FIELD` — the clone carries no wt-33 fillA-mode7 body record, or no wt-8 value widget, to isolate
- `NO_DISPLAY_CELL` — fewer than 3 `+0x44BC8` indices are both widget-spare and gauge-level-free, or `sramreach.free_runs` found no fresh SRAM
- `UNEXPECTED_APPEND_POINT` — the GuiCode append point is below stock's 0x00259BB4 or misaligned (`_check_append_point`)
- `ROUTINE_REFUSED` — `voltagebattery.build_routine` refused (a bad constant or a mis-aligned code load address)
- `GROW_REFUSED` — `growsection.grow_section` refused the GuiCode append
- `DETOUR_REFUSED` — the bytes at the per-tick hook were not the stock/chained `bl` `followchannel.hook_state` expected (a grow shifted something)
